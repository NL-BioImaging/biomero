This class extends the Connection class, adding methods and attributes specific to working with Slurm.

cancel_slurm_jobs(slurm_job_ids: List[int]) → Result | None[source]

Cancel Slurm jobs, for example when the workflow they belong to is cancelled.

Cancelling a job that already ended is not an error for the caller: the job is gone either way, so this logs what Slurm answered and returns the result instead of raising.

The command restricts scancel to jobs owned by the cluster account BIOMERO connects with (--user, which Slurm documents as “restrict the scancel operation to jobs owned by the given user”). An account with Slurm operator, admin or coordinator rights may otherwise cancel other users’ jobs, so a wrong or stale job ID can never hit a job that is not BIOMERO’s. It uses --user="$USER" rather than --me, which older Slurm versions lack.

Parameters:

slurm_job_ids (List[int]) – The job IDs of the jobs to cancel.

Returns:

The result of the scancel command, or None when none

of the IDs is a valid job ID.

Return type:

Result

  • end_time (str) – The end time until which to retrieve job information. Defaults to “now”.

  • columns (str) – The columns to retrieve from the job information. Defaults to “JobId”. It is comma separated, e.g. “JobId,State”.

  • states (str) – The job states to include in the query. Defaults to “r,cd,f,to,rs,dl,nf”.

claim_launcher_task(task_id: UUID, owner: str, lease_seconds: float = 300) → bool[source]

Claims a launcher task for a supervisor, atomically.

This is a compare-and-set on the task’s event stream: the claim is appended as the next event of the task, and the event store accepts only one event per position. When two supervisors read the same task and both try to claim it, one of them loses and gets False.

A claim is valid for lease_seconds. The owner renews it by claiming again; a claim that was not renewed (for example because the supervisor crashed) can be taken over by any other owner. Renew well within the lease (the processor renews three times per lease). The lease compares the claim’s timestamp with this process’s clock, so supervisors must have clocks that agree to well within the lease; the event-store position, not the clock, is what keeps two claims apart.

Parameters:

  • task_id (UUID) – The launcher task to claim.

  • owner (str) – Identity of the claiming supervisor.

  • lease_seconds (float, optional) – How long a claim stays valid. Defaults to constants.LAUNCHER_CLAIM_LEASE_SECONDS.

Returns:

True when the caller now holds the claim.

Return type:

bool

Raises:

ValueError – If the task is not a launcher task.

biomero.detached module

The detached-mode setting, and aliases for names that moved.

A BIOMERO workflow run outlives the OMERO session that asks for it, so a script can queue the run in a launcher task and a supervisor (the OMERO processor in NL-BIOMERO) executes it. Core only provides the mechanisms:

  • the launcher marker and rule: constants.LAUNCHER_MARKER, WorkflowTracker.add_launcher_task and eventsourcing.is_launcher_task;

biomero.maintenance module

Durable metadata-maintenance requests, separate from analysis workflows.

Only plain request options and compact outcomes are persisted. The processor owns execution; the scripts layer owns all external annotation operations.

Why this is in core and not in the processor or the scripts: a request is an aggregate in the WorkflowTracker event store, next to the workflow aggregates. Every projection of that store (biomero.views) resolves the class of each event it reads from the event’s stored topic, and the topic is the import path of the class: biomero.maintenance:MetadataRefresh.Started and so on. A class that only the processor or a script can import would make every other process that replays the store fail on these events, and moving the class would orphan the requests already stored. The request lifecycle (this aggregate and its notification scan) therefore stays here; running a request does not.

biomero.ssh_recovery module

Bounded recovery from interrupted SSH connections.

An SSH connection to the cluster can drop while a Slurm job keeps running. This module retries an operation that is safe to repeat, within a time window (ssh_recovery_timeout), and stops with a clear error when the window ends. A window of 0 means no retries: the same code runs once and raises the original error.

Only transport loss is retried: never authentication, never a command that failed on the cluster, and never an arbitrary command. The caller decides which operations are safe to repeat and wraps them in retry. The Slurm side (never submitting twice) lives in SlurmClient and remote_scripts.

biomero.remote_scripts module

Shell scripts that BIOMERO runs durably on the cluster.

After a lost SSH connection a caller cannot know whether its remote command ran. These builders make a command safe to ask again: it runs under a lock and leaves a marker or receipt file, so that a second request finds the first result instead of repeating the work (for example a second sbatch).

The builders only create strings and know nothing about connections; the caller (SlurmClient) runs them. Each script is built from small named parts, so you can read what it does without tracing nested quotes.

Receipt protocol of submit_once_script. All files share one prefix, the state prefix (<slurm_data_path>/.biomero-recovery/<task id>):

  • .lock: the lock file; one submission per prefix runs at a time.

  • .digest: hash of the command, to notice a changed command on resume.

  • .intent: written BEFORE sbatch runs. It holds the submission time. An intent without a .job means the outcome of sbatch is unknown.

  • .job: the Slurm job id, published atomically once known.

  • .failed: sbatch refused the job (no job exists); keeps the output.

  • .stdout / .stderr: the output of the sbatch call.

Exit codes with a meaning to the caller: REMOTE_BUSY_EXIT_CODE (the lock is held elsewhere, or the job is not visible in Slurm yet; ask again later) and SUBMISSION_REJECTED_EXIT_CODE (sbatch refused the job).
